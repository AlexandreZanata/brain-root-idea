## Outcome and design direction

Make the existing BrainRoot frontend feel coherent, quiet, and effortless: one clear primary action per view; a visually dominant Companion Canvas; a readable conversation; consistent alignment, spacing, typography, states, and controls; and no decorative clutter. Preserve every working B18 capability and the product's agent-first journey. This is a design-system refinement, **not** a redesign into an IDE, a generic AI SaaS dashboard, or a copy of another product.

The divider is the **edge between chat and Canvas**, not a visible drag button. [B18-R01](https://github.com/AlexandreZanata/brain-root-idea/issues/110) already changed B18-S03's pending contract to implement that behavior before B19. B19 audits/refines the released edge; it must not implement and then remove a redundant handle. If B18 releases with a visible handle, treat its removal as B19's first tracked correction and verify keyboard/focus/gesture access before any cosmetic work.

## Evidence-based reference kit (reviewed 2026-09-24)

Use these as **rules and inspection examples**, not libraries to install, CSS to paste, or brands/assets to clone. Keep BrainRoot's Apache-2.0 license/NOTICE and its own visual identity. The two project source snapshots are pinned so an economical agent does not accidentally rely on later moving branches.

1. [GNOME HIG — Design Principles](https://developer.gnome.org/hig/principles.html) and [Navigation](https://developer.gnome.org/hig/guidelines/navigation.html): one clear purpose per view, progressive disclosure, frequently used actions close to the work, and simple navigation. Apply to BrainRoot's header/rail/composer/Canvas control density; do **not** import GNOME branding or GTK widgets.
2. [GNOME HIG — Buttons](https://developer.gnome.org/hig/patterns/controls/buttons.html), [Typography](https://developer.gnome.org/hig/guidelines/typography.html), and [Scaling & Adaptiveness](https://developer.gnome.org/hig/guidelines/adaptive.html): adjacent peer buttons should share width; use few text sizes/weights and system fonts; check constrained window sizes. BrainRoot's exact sizing/typography below is its own contract, not a wholesale Adwaita theme.
3. [IBM Carbon — Spacing](https://carbondesignsystem.com/elements/spacing/overview/) and [Button usage](https://carbondesignsystem.com/components/button/usage/): semantic spacing makes groups/hierarchy legible; related button groups use the same size/width and a single high-emphasis action. Borrow the principle, not Carbon React/Sass or its visual skin.
4. [W3C WAI-ARIA Window Splitter pattern](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/) and [WCAG 2.2](https://www.w3.org/TR/WCAG22/) (reflow, focus, dragging alternative, pointer target size): the invisible edge must still be discoverable, focusable, and operable without dragging. The APG splitter pattern notes its functional example is not complete; use it as guidance, and validate actual semantics on BrainRoot's Linux stack rather than claiming conformance by association.
5. [Penpot design tokens](https://help.penpot.app/user-guide/design-systems/design-tokens/) and [component variants](https://help.penpot.app/user-guide/design-systems/variants/), real [Penpot source snapshot `84e651c`](https://github.com/penpot/penpot/tree/84e651c2312d9f8608c7f6f1f36a17a7a2b6d9cf) (MPL-2.0): one token/variant vocabulary can keep light/dark, size, emphasis, and states synchronized. Inspect the model only; do not copy MPL source into BrainRoot.
6. Real [Excalidraw source snapshot `dc2c16d`](https://github.com/excalidraw/excalidraw/tree/dc2c16d9e2073078cb4b8f3dce942133b90eec3d) (MIT; [project README](https://github.com/excalidraw/excalidraw/blob/master/README.md)): inspect how Canvas controls can be contextual while the work surface stays dominant, and how tool actions remain real controls. Excalidraw is a whiteboard, not a browser or agent UX; do not copy its iconography, canvas runtime, or layout wholesale.
7. BrainRoot's earlier [Freebuff release-reference plan](freebuff-inspired-experience-plan.md) remains conceptual UX context only. The publicly released Desktop app's corresponding source was not available in the inspected snapshot, so its internal architecture and exact UI implementation remain `UNKNOWN`; do not present it as reusable code or measured performance evidence.

Before a B19 issue uses a reference, its author records the exact linked section, the one BrainRoot rule it justifies, and an explicit **do-not-copy** note. External recommendations do not override BrainRoot's own measured budgets or security model.

## Fixed visual and interaction contract

These values are proposed **TARGETS**, not measurements. B19-S00 must compare them with the final B18 UI and record any approved adjustment before code changes; B20-S00 repeats the check against the released B19 UI.

- **Hierarchy:** Canvas remains visually dominant; chat is the adjacent intent/progress surface. One high-emphasis action per view or form. Secondary actions are quiet; destructive/rare actions appear in a clearly labelled secondary disclosure, never hidden behind an unlabeled icon. Do not hide failures, permission decisions, or Undo/recovery cues.
- **Spacing:** use a small semantic scale based on `4 / 8 / 12 / 16 / 24 / 32` CSS px, expressed as `rem` where appropriate. A parent container owns the gap between siblings; individual children do not each add arbitrary margins. Alignment follows common edges and text baselines. Do not stack borders/cards where spacing alone establishes a group.
- **Typography:** continue to use the system font without a new webfont. Use a restrained family of body `14–16px`, supporting text at least `12px`, panel heading `16px`, and app title around `20px`, with consistent line heights. Avoid the current sub-12px badges/labels; keep technical detail readable without making it the default focal point. Respect OS text scaling. **Superseded for the floor by B20-U1 (2026-09-25):** the 12px floor is now 13px, because the pinned OpenCode theme's smallest step is `--font-size-small: 13px` and it has no 12px step. See `../../22-opencode-ui-parity.md`.
- **Surfaces:** preserve the existing light/dark brand palette unless a contrast failure requires a scoped adjustment; use a small neutral surface hierarchy (window, panel, raised control) and the existing accent, not a rebrand. Proposed restrained radii: controls `6px`, panels `10px` where appropriate; no glassmorphism, heavy shadows, gradients, neon, decorative animation, or large permanent badges. Color is never the only state signal.
- **Controls:** any buttons adjacent in the same action row/group have the **same height and equal widths** determined by the longest label or available grid track, even when one is primary; field+button rows align to the same height and baseline. Suggested standard pointer height is `40px` and compact toolbar height `36px`; icon-only controls are square with an accessible name and visible focus, and only use a recognizable icon. On constrained widths, the whole group wraps/stacks while preserving equal peer sizes, rather than one button shrinking alone. If equal sizing harms reflow, separate the actions into distinct groups or stack them; do not create an unequal side-by-side exception. Keep one primary action, not multiple competing white/blue fills. Target at least WCAG 2.2 AA pointer geometry and visible contrast; test actual controls, not CSS tokens alone.
- **Edge divider:** no discrete visible button/thumb. A restrained border marks the boundary, with a forgiving hit region and subtle hover/drag feedback, keyboard equivalent, and a clear focus ring/line. Preserve B18's cleanup/frame/one-HOT guarantees. Gesture code owns only shell chrome, never remote page input.
- **States:** idle, loading, ready, empty, stale/COLD, error, permission denial, disabled, hover, focus, pressed, and reduced-motion appearances are defined for each applicable component. The copy says what the user can do next; technical codes stay in Technical details. A loading indicator must correspond to actual work, not a fake timer.
- **Responsive layout:** validate at 320, 640, 1024, 1440, and 1920 CSS px equivalent widths and at 200%/400% zoom where feasible. Never truncate the primary action or obscure focus; the Canvas and conversation may stack, but the real native Browser/Preview stays inside its declared slot. Do not add permanent panels to fill wide empty space.
- **Resource cost:** no new runtime UI framework, font package, icon pack, CSS framework, animation library, or always-on observer. CSS transitions should be restrained (`120–180ms` for color/opacity only) and disabled for reduced motion. Report JS/CSS bundle deltas, startup, settled idle CPU/PSS, input feedback, native bounds traffic, and WebView lifecycle against a **same-session B18 baseline**. A “prettier” UI that regresses the release budgets without a documented exception fails.

## Strict issue and release evidence

Each issue must include a source/target screenshot or explicit visual-state description, exact allowed files, a short user-facing outcome, negative/failure state, keyboard/focus/reduced-motion path, text-length/zoom/narrow-window case, performance risk, rollback, and test cases written now but deferred. The fast micro-gate is the allowlisted `git diff --name-only <issue-start-SHA>...HEAD`, `git diff --check`, `sh scripts/check-docs.sh`, `sh scripts/check-security.sh`, `sh scripts/check-accessibility.sh`, and `pnpm run check` for TypeScript/Svelte edits. Do **not** call `scripts/check-fast.sh` per issue: it runs automated tests. Record `IMPLEMENTED_UNVERIFIED`, not “tested”.

At the B19 release gate, check all **foundation/shell** states (themes, narrow/wide, header, rail, composer, Swap, edge hover/focus/drag, keyboard, reduced motion, high contrast, large text). At the B20 release gate, check the **complete frontend**: first-run empty, active conversation, loading/failure, Browser phone page, Preview phone page, swapped sides, permission denial, and data-clear confirmation in both themes, narrow/desktop widths, keyboard-only, reduced motion, high contrast, and large text. Check related buttons' bounding boxes: equal height and equal width within every adjacent action group; a responsive stack is checked as a group at that width. Check W3C/WCAG criteria by behavior, not by visual impression. Capture sanitized screenshots and raw measurements; never include real browser profiles, credentials, URLs with secrets, or project content.

Performance figures remain `TARGET` or `UNKNOWN` until each release report records the environment, raw samples, median/p95/range, and process-tree accounting per [the performance contract](../10-performance-budget.md). Proposed TARGET: **zero** new runtime dependencies and always-on resources; no heavy WebView recreation from styling; no material startup/idle regression against the previous release in the same session; input feedback within one display frame; bundle deltas explained. If the baseline already misses a global budget, visual polish must report it honestly and not describe it as fixed.

## Stop conditions and reversibility

Stop rather than improvise if a requested improvement needs a Rust/core change, a new dependency or external asset, changes an existing security/permission boundary, violates the one-HOT/browser isolation contract, makes focus order confusing after Swap, hides an essential action or failure, cannot meet the equal-button-group rule without harming reflow, or requires testing against private data. Escalate with a screenshot/fixture, specific alternatives, and a scoped issue/ADR. Revert only the responsible microstep with a tracked commit; preserve user data and public history. This plan is independent preparatory work and must not be merged or treated as an executable B19 batch ahead of B18.
