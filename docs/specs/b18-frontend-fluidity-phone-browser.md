# B18 proposal — fluid Canvas, phone-first browser

- **Status:** proposed frontend-only Linux batch; not an executable issue or a released capability
- **Baseline:** `main` at `5f2835c` (`v0.0.13`, B17 complete)
- **Batch branch/PR:** `batch/b18-fluid-canvas` / one Draft PR
**Related:** [Companion Browser plan](companion-browser-plan.md), [Canvas](../05-companion-canvas.md), [performance contract](../10-performance-budget.md), [execution protocol](../18-mvp-execution-plan.md), [ADR 0014](../adr/0014-release-only-test-cadence.md)

## User outcome and boundaries

On Linux, BrainRoot opens with the **Browser** destination selected beside chat, in a centered **phone-width responsive viewport**. The user can resize the divider smoothly, put the Canvas on either side with **Swap**, and move between Browser and Preview with a horizontal swipe on **Canvas chrome** or an equivalent button/keyboard action. Entering an address opens the **existing real, isolated Human Browser WebView**, not an iframe, screenshot, or imitation. Preview continues to run a real localhost project page and defaults to phone width when selected. The Canvas stays visually dominant and the interface remains an agent-first product, not a miniature IDE.

“Swap sides”, “drag divider”, and “swipe destination” are three different actions. A gesture starting inside web content must remain the page's gesture. Phone width means responsive viewport only; no claim of Android/iOS engine, touch, DPR, user agent, or device API emulation. No Chrome/Firefox profile import, credentials, downloads, popups, new provider, Rust/core change, extra dependency, telemetry, or second HOT content view belongs in B18.

### Native-browser startup decision

The existing Human Browser core accepts only user-directed `http`/`https`; `human_browser_show` requires a URL and bounds, while `about:blank`, `file:`, and application-internal schemes are denied. Therefore **Browser selected at launch does not mean a remote page is fetched or a native content WebView is allocated at launch**. The first explicit address creates the real WebView inside the phone-sized slot. This is the only frontend-only, no-surprise-network behavior compatible with current policy and the one-HOT resource invariant. Do not auto-open an arbitrary public website, copy a user's installed browser profile, or route remote content into the privileged shell.

If the maintainer instead requires an already-created *blank native WebView* on every launch, stop this batch before implementation: that needs a separately approved Rust navigation/start-page policy, lifecycle and memory benchmark, and likely a new ADR. Do not fake the requirement with an iframe or screenshot. A ready project preview may take focus automatically only if the user has not already chosen a Canvas destination in this session; it must not unexpectedly replace an actively used Browser.

## Current code facts (inspection, not runtime measurements)

- `CanvasPanel.svelte` starts on Preview; `PreviewPanel.svelte` starts on Desktop. `HumanBrowserPanel.svelte` has a full-width slot and creates the real WebView only after the user enters an address.
- `PanelResizer.svelte` is a native vertical range input. The workspace has fixed 280–560 px chat bounds and stacks below 1080 px; there is no side Swap or Canvas-chrome swipe.
- Both content panels observe size and schedule bounds at `requestAnimationFrame`, but native bounds calls are asynchronous. The plan must avoid overlapping stale writes and ensure the final rectangle is applied.
- B12 measured inexpensive native preview bounds updates, and B15 measured one-HOT Deck switching. Neither result measures a user's continuous divider drag, swipe responsiveness, Browser phone geometry, or the CPU/RAM of Browser-as-default. Those results remain `UNKNOWN` until B18's release gate.
- B17 release evidence reports a 266.3 MB process-tree PSS median and an idle CPU median of 1.724% on a busy host; the original 150 MB and <1% targets were not met. B18 must not advertise “lightweight” as a measured fact without same-session comparison.

## Fixed interaction contract

1. **Initial state:** Browser tab selected, phone preset selected, no remote request or child content WebView until an address is entered. Canvas remains larger than chat at normal desktop widths; narrow layouts stack without horizontal overflow. A selected Preview uses its own phone-width default and only starts a dev server on explicit project action.
2. **Divider:** hit area is discoverable and at least 24 CSS px wide without adding permanent visual bulk. Pointer drag uses capture on the shell handle, clamps to available width and documented minimums, coalesces visible changes to at most one animation frame, and commits the final value on release/cancel. Keyboard arrows and Home/End provide the same range; screen readers receive a meaningful label and current value. A lost pointer, Escape, window blur, or component teardown leaves no capture/listener/frame behind. No global selection ban.
3. **Swap:** one explicit control reverses visual sides without destroying/remounting Canvas or the active WebView, resetting the address, moving a running dev server, or changing which destination is selected. Announce the new side. Check logical keyboard order against visual order on both sides; if the focus path becomes confusing, the release gate fails.
4. **Swipe:** only a dedicated Canvas header/chrome zone owns horizontal gestures. Require horizontal intent and distance/velocity threshold; vertical scroll, text selection, page drag, and gestures inside the native WebView are untouched. Buttons and keyboard can always select the same destination. Reduced motion uses direct state changes. A destination change may COLD-recreate the old view under the existing one-HOT policy and must keep B17's honest reload/state-loss message.
5. **Phone viewport:** center an actual native content rectangle at the available phone width (390 CSS px target, clamped to the Canvas area), report the actual width when constrained, and size Preview and Human Browser consistently. Do not use CSS transform scaling to simulate a device. Resize/swap changes geometry through existing `set_bounds` commands; no reload solely to alter width. Hide/destroy only through existing role lifecycle.
6. **Cost:** no animation loop, observer, gesture listener, IPC storm, dev server, or extra WebView persists when the relevant surface is inactive. Bounds requests use at most one in flight plus one latest pending rectangle, suppress duplicate rectangles, and apply the final rectangle after drag/resize; stale command results must not overwrite newer navigation status. A failed bounds call gives an understandable retry state or a safe recovery path, not a silent permanent misalignment.

## Release measurement and pass criteria

Use a release build with debug tooling off and the [performance report template](performance-test-template.md). Record commit, hardware, OS/display stack, WebKitGTK, power/background load, fixture URL served by a local disposable HTTP server, exact commands/instrumentation, raw samples, and process tree. Do not use a live profile, account, or external network. Measure both baseline B17 and candidate B18 in the **same session**; the historical B17 numbers are context, not a statistically controlled before/after comparison.

- **TARGET: responsiveness:** local divider feedback reaches the next 60 Hz frame (16.7 ms) at p95; no continuous work after release. Record event-to-paint samples and missed-frame distribution, not a subjective “smooth” label. If the reference display uses a different refresh rate, report its frame budget separately.
- **TARGET: native work bound:** at most one bounds IPC in flight and one pending latest rectangle, no duplicate bounds call, exactly the final rectangle after each completed gesture. Zero WebView recreation or page reload from divider/SWAP alone; verify with a local page marker and actual `innerWidth`, not a CSS mock.
- **TARGET: startup/idle:** no extra heavy content WebView or network request before explicit navigation; startup and settled idle CPU/PSS must not regress beyond same-session noise. Report shell, Browser WebView, and fixture server costs separately. Any material regression needs an explicit maintainer decision before merge.
- **TARGET: lifecycle:** one HOT heavy content WebView, zero orphaned resources after 100 resize/swap/tab cycles and close; compare child counts and PSS before/after, including the first-use WebKit context cache separately.
- **Accessibility/security:** pointer, keyboard, screen-reader and reduced-motion paths checked on the Linux reference stack; no remote Tauri IPC, no page-gesture theft, no hidden profile import, no new permission or dependency. Manual focus escape from the child WebView remains an explicit release check; a failure is a blocker, not an undocumented exception.

The existing `docs/10-performance-budget.md` budgets remain in force. An unattained budget is recorded as a failure or approved exception with owner/expiry, never silently relaxed. Tests and full CI run at S07 only; after submitting Ready, record `CI_PENDING` and continue other independent work without waiting.

## Stop and rollback

Stop the affected issue if the existing core cannot keep native geometry correct without a Rust change, if the browser must load a page at launch, if a gesture must intercept remote-page input, if a second HOT view is needed, if startup/idle cost materially rises, or if the file allowlist/ADR/security boundary must change. Open a scoped decision/remediation issue; do not expand B18 silently. Revert only the offending microstep commit or turn off its frontend entry point in a tracked follow-up; preserve the prior B17 experience and do not rewrite public history.
