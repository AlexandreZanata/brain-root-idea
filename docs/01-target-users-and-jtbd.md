# Target users and jobs to be done

## Primary users

### Intent-led builder

Knows what a product should do and look like but has limited knowledge of code, Git, terminals, or deployment. Judges success by using the result.

**Job:** “When I have an idea, help me turn it into working, editable software without making me become an IDE operator.”

### Vibe coder

Already builds through AI prompts, can recognize obvious failures, and values speed, experimentation, visual feedback, and undo more than manual control of every file.

**Job:** “Let me direct an agent, watch the app, test it, and recover quickly when a change goes wrong.”

### Emerging developer

Understands some technical concepts but expects visual, conversational, multitasking interfaces. May progressively reveal code and logs.

**Job:** “Give me a simple default and let me inspect how the project works when I am ready.”

## Secondary user

An experienced developer may use BrainRoot for delegation and observation. Developer Mode can expose code, diffs, terminal, Git, processes, and diagnostics, but this user's existing IDE habits do not set the default information architecture.

## Core jobs

- Start or open a normal software project.
- Turn a natural-language outcome into safe, visible work.
- See the actual application, not merely a description of changes.
- Correct the result through direct feedback.
- Understand whether work is progressing, blocked, tested, or complete.
- Review and undo meaningful changes without learning Git.
- Resume a project and conversation after closing BrainRoot.
- Reveal technical evidence when trust or debugging requires it.

## User anxieties to resolve

- “Will the agent delete or expose something important?”
- “Is it actually working or only talking?”
- “How do I get back to the version that worked?”
- “Why did the app stop?”
- “Am I trapped in this tool?”
- “Will this make my computer slow?”

## Deliberate non-targets for the first release

- Teams needing multiplayer editing, enterprise policy management, or cloud workspaces.
- Developers seeking a complete replacement for a mature text editor and extension ecosystem.
- Users expecting mobile development from a mobile device.
- Fully autonomous, unattended production operations.

## Accessibility and inclusion

Nontechnical must never mean imprecise or inaccessible. Core flows must support keyboard-only use, screen-reader semantics, visible focus, reduced motion, zoom, readable contrast, and language that does not rely on programming knowledge. Gesture-only Deck navigation must always have explicit controls.
